# داشبورد مدیریتی مجتمع خراسان — راهنمای راه‌اندازی

داشبورد وب آفلاین بر پایهٔ ۳۰ شاخص گزارش جامع، متصل به **Ollama** روی همان رایانه.
بدون هیچ وابستگی اینترنتی — نه در اجرا، نه در تحلیل، نه در نمودار.

---

## ۱. نصب در چهار گام

```bash
# ۱) پیش‌نیازها
pip install -r requirements.txt

# ۲) اجرا
python run.py

# ۳) مرورگر
#    http://127.0.0.1:8000
```

**پیش‌نیاز Ollama:** باید نصب و در حال اجرا باشد (روی ویندوز آیکونش در سینی سیستم دیده می‌شود).

```bash
# مدل‌ها را یک‌بار دانلود کنید (نیاز به اینترنت، فقط همین یک‌بار)
ollama pull qwen3.5:4b      # گفت‌وگو و پاسخ سریع  (~۲٫۵ گیگ)
ollama pull qwen3.5:9b      # تحلیل صفحه‌ها        (~۵٫۵ گیگ)
ollama pull gemma4:12b      # تحلیل عمیق (اختیاری) (~۷٫۵ گیگ)
```

**بررسی اتصال:**

```bash
curl http://127.0.0.1:11434/api/tags
```

اگر پاسخ داد، داشبورد هم وصل می‌شود. اگر Ollama روی رایانهٔ دیگری است:

```bash
# ویندوز
set OLLAMA_HOST=http://192.168.1.10:11434
# لینوکس / مک
export OLLAMA_HOST=http://192.168.1.10:11434
python run.py
```

> روی سرور راه‌دور باید `OLLAMA_HOST=0.0.0.0` هم در سرویس Ollama تنظیم شود، وگرنه اتصال رد می‌شود.

## ۳. معماری

```
منابع داده (فایل‌های موجود / قالب اکسل / فرم)
        ↓
   دروازهٔ ورود  ←  اعتبارسنجی + نسخه‌بندی
        ↓
   SQLite (data/dashboard.db)
        ↓
   موتور شاخص  ←  catalog.py (۳۰ فرمول ثابت)
        ↓
   لایهٔ قواعد  ←  rules.py (هشدار قطعی، ۹ قاعده)
        ↓
   داشبورد  +  تحلیل Ollama
```

**قاعدهٔ طلایی:** مدل زبانی هیچ عددی حساب نمی‌کند. فقط بستهٔ واقعیت را می‌خواند و متن می‌نویسد. هر عددی که در پاسخ بیاید و در بستهٔ واقعیت نباشد، در نوار پایین تحلیل با رنگ قرمز علامت می‌خورد.

## ۶. ورود اطلاعات

### راه اول — قالب اکسل (مسیر روزمره)

1. صفحهٔ «کیفیت و ورود داده» → دانلود قالب (۸ قالب)
2. پر کردن ستون **مقدار** — بقیه ستون‌ها لیست کشویی دارند
3. بارگذاری همان فایل در همان صفحه
4. اعتبارسنجی ← REPORT خطا (اگر بود) ← ثبت نسخه ← بازمحاسبهٔ خودکار شاخص‌ها

**قاعدهٔ ماه:** ماه `۰` = جمع دوره، `۱..۶` = فروردین تا شهریور.
**سناریو:** `ACT` عملکرد، `BUD` بودجه، `LY` دوره مشابه.

### راه دوم — ورود دستی

```bash
curl -X POST http://127.0.0.1:8000/api/data/fact \
  -H "Content-Type: application/json" \
  -d '{"branch":"لطف آباد","code":"OPS.TRN.EXP","year":1405,"month":3,"value":98400}'
```

### راه سوم — درون‌ریزی اولیه (خودکار)

در اولین اجرا، دادهٔ سه سال از فایل‌های موجود بارگذاری می‌شود: ۳٬۲۲۶ قلم داده → ۳۹۰ شاخص.

## ۹. نکات نگهداری

- **پشتیبان‌گیری:** فقط `data/dashboard.db` را کپی کنید. همه‌چیز در همان یک فایل است.
- **بازنشانی داده:** فایل پایگاه داده را پاک کنید؛ در اجرای بعد از نو ساخته و درون‌ریزی می‌شود.
- **تغییر مدل:** در `app/config.py` یا با متغیر محیطی `MODEL_ANALYSIS`.
- **افزودن شاخص:** یک سطر در `catalog.KPI_CATALOG` + یک `put()` در `engine.compute_branch`.
- **قفل دوره:** جدول `data_version` ستون `locked` دارد؛ برای فعال‌سازی، بررسی آن در `save_fact` کافی است.

## ۱۰. محدودیت‌های شناخته‌شده

1. **بودجه فقط برای دو شاخص** در دسترس است (سود پرسنلی و تناژ)؛ بقیه با قالب بودجه کامل می‌شوند.
2. **دادهٔ تیر تا شهریور** در فایل‌های موجود نبود؛ ساختار آماده است و با ورود داده پر می‌شود.
3. **درصد اشغال بالای ۱۰۰٪** در برخی شعب، تناقض داده است — نه باگ برنامه. هشدار R11 آن را نشان می‌دهد.
4. **تحلیل روی CPU کند است** — کش و پیش‌تولید الزامی است، نه اختیاری.
5. **خروجی PPTX** هنوز به داشبورد وصل نشده؛ سازنده‌های فعلی گزارش جدا اجرا می‌شوند (فاز ۳).

## عیب‌یابی: «مرورگر Ollama را می‌بیند ولی داشبورد نه»

اگر `http://127.0.0.1:11434` را در مرورگر باز می‌کنید و پیام «Ollama is running» را می‌بینید
اما نوار کنار داشبورد می‌گوید «در دسترس نیست»، سه علت ممکن است. به‌ترتیب احتمال:

### ۱) برنامه روی رایانهٔ دیگری اجرا شده (شایع‌ترین)
اگر داشبورد را از یک پیش‌نمایش ابری یا سرور دیگر باز کرده‌اید، مرورگر شما به
`127.0.0.1` روی **رایانهٔ خودتان** می‌رود، ولی برنامهٔ داشبورد به
`127.0.0.1` روی **آن سرور** می‌رود — که Ollama ندارد.
نسخهٔ ۱٫۱ این حالت را تشخیص می‌دهد و پیام «روی رایانهٔ Ollama اجرا نشده» را نشان می‌دهد.
**راه‌حل:** داشبورد را روی همان رایانه‌ای اجرا کنید که Ollama روی آن است.

### ۲) پروکسی یا VPN سیستم
ابزارهای عبور از تحریم و VPN معمولاً متغیرهای `HTTP_PROXY` / `ALL_PROXY` را تنظیم می‌کنند.
در این حالت درخواست به `127.0.0.1` هم از پروکسی عبور داده می‌شود و شکست می‌خورد،
در حالی که مرورگر localhost را دور می‌زند. **این باگ در نسخهٔ ۱٫۱ رفع شده**
(همهٔ تماس‌ها با `trust_env=False` انجام می‌شوند).

اگر نسخهٔ قدیمی دارید، موقتاً پروکسی را خالی کنید:
```bat
set HTTP_PROXY=
set HTTPS_PROXY=
python run.py
```

### ۳) Ollama روی IPv6 یا پورت دیگری گوش می‌دهد
نسخهٔ ۱٫۱ به‌ترتیب این نشانی‌ها را آزمایش می‌کند و اولین نشانیِ پاسخ‌ده را
خودکار انتخاب می‌کند:
`OLLAMA_HOST` → `127.0.0.1` → `localhost` → `[::1]` → `host.docker.internal`

### ابزار عیب‌یاب
```bash
python diagnose_ollama.py
```
خروجی نمونه:
```
۲) آیا سرویس روی پورت ۱۱۴۳۴ گوش می‌دهد؟
  ✓ 127.0.0.1:11434 → باز است
  ✗ ::1:11434 → بسته است
۳) پاسخ HTTP
  ✓ http://127.0.0.1:11434 → 8 میلی‌ثانیه، 5 مدل
۴) پروکسی سیستم
  ! پروکسی فعال است: http://127.0.0.1:10808
  ✗ با فعال بودن پروکسی، اتصال به Ollama قطع می‌شود → همین علت مشکل است
۵) مدل‌های لازم
  ✓ qwen3.5:4b موجود است
  ✓ qwen3.5:9b موجود است
```

### تغییر نشانی Ollama
اگر Ollama روی رایانهٔ دیگری در شبکه است:
```bash
set OLLAMA_HOST=http://192.168.1.50:11434
python run.py
```
و روی آن رایانه، Ollama باید روی همهٔ رابط‌ها گوش بدهد:
`OLLAMA_HOST=0.0.0.0 ollama serve`

### ۴) خطای ۴۰۴ روی `/api/chat`

```
HTTPStatusError: Client error '404 Not Found' for url 'http://127.0.0.1:11434/api/chat'
```

این خطا **یعنی اتصال برقرار است** — ولی Ollama حاضر به پاسخ نیست. دو علت:

**الف) مدل نصب نیست (شایع‌ترین).** Ollama برای مدلی که وجود ندارد، کد ۴۰۴ با
پیام `model "qwen3.5:9b" not found` برمی‌گرداند. یعنی داشبورد مدل پیش‌فرض
(`qwen3.5:9b`) را خواسته ولی شما آن را دانلود نکرده‌اید.
```bash
ollama pull qwen3.5:9b
```
از نسخهٔ ۱٫۲، برنامه این حالت را خودکار تشخیص می‌دهد و با مدلِ **نصب‌شدهٔ**
موجود تحلیل را انجام می‌دهد، با یادداشت صریح:
«مدل «qwen3.5:9b» نصب نیست؛ تحلیل با «qwen3.5:4b» انجام شد.»

**ب) نسخهٔ بسیار قدیمی Ollama.** مسیر `/api/chat` از نسخهٔ ۰٫۱٫۲۴ (دی ۱۴۰۲)
اضافه شده. اگر نسخهٔ قدیمی‌تر دارید، به‌روزرسانی کنید. از نسخهٔ ۱٫۲ برنامه،
در این حالت خودکار به مسیر قدیمی `/api/generate` سوئیچ می‌کند و کار متوقف نمی‌شود.

### کدام مدل‌ها لازم است؟
| نقش | مدل | پیش‌فرض |
|---|---|---|
| گفت‌وگو | `qwen3.5:4b` | ~۲٫۵ گیگابایت |
| تحلیل پنل | `qwen3.5:9b` | ~۵ گیگابایت |
| عمیق (اختیاری) | `gemma4:12b` | ~۷ گیگابایت |

اگر فقط یکی را دارید، همان یکی کافی است — برنامه خودش آن را انتخاب می‌کند.

## نسخهٔ برنامه

از نسخهٔ ۱٫۳ شمارهٔ نسخه در **پایین نام «مجتمع خراسان»** در نوار کناری دیده می‌شود.
اگر آن عدد را نمی‌بینید، یعنی نسخهٔ قدیمی‌تری اجرا شده است.

| نسخه | چه چیزی اضافه شد |
|---|---|
| ۱٫۰ | نسخهٔ اول: ۳۰ شاخص، ۹ صفحه، ۸ قالب اکسل |
| ۱٫۱ | رفع قطع اتصال Ollama با پروکسی سیستم؛ عیب‌یاب مستقل |
| ۱٫۲ | انتخاب خودکار مدلِ نصب‌شده؛ رفع خطای ۴۰۴ |
| ۱٫۳ | نمایش نسخه در رابط کاربری + پنل عیب‌یابی داخل داشبورد |

### پنل عیب‌یابی
دکمهٔ **«عیب‌یابی»** در کادر «هوش مصنوعی محلی» (نوار کناری) باز می‌شود و
هفت چیز را جداگانه بررسی می‌کند:

```
✓ سرویس Ollama        پاسخ در ۹ میلی‌ثانیه
✓ نشانی               http://127.0.0.1:11434
✓ پروکسی سیستم        تنظیم نشده
✓ مدل گفت‌وگو          qwen3.5:4b نصب است
✗ مدل تحلیل           qwen3.5:9b نصب نیست — ollama pull qwen3.5:9b
✗ مدل عمیق             gemma4:12b نصب نیست
✗ تولید متن           مدل «qwen3.5:9b» روی این Ollama نصب نیست
```

دکمهٔ **«کپی متن»** همین گزارش را در کلیپ‌بورد می‌گذارد تا برای بررسی بفرستید.

### بررسی پیش از اجرا
```bash
python run.py --check
```
بدون اجرای سرور، پیش‌نیازها را بررسی می‌کند:
پایتون، بسته‌ها، فایل‌های داده، فونت و Ollama.

## سرعت روی CPU — و چرا مدل را در حافظه نگه می‌داریم

بار اولی که مدل بارگذاری می‌شود، Ollama فایل ۵ گیگابایتی را از دیسک می‌خواند.
روی i5-12400 این کار **۳۰ تا ۶۰ ثانیه** طول می‌کشد. اگر مدل آزاد شود، تحلیل بعدی
دوباره همین معطلی را دارد.

از نسخهٔ ۱٫۴، هر درخواست با `keep_alive` فرستاده می‌شود (پیش‌فرض `30m`)؛
یعنی مدل بعد از تحلیل **۳۰ دقیقه در حافظه می‌ماند** و تحلیل صفحهٔ بعدی
بدون معطلی شروع می‌شود.

تغییر مدت نگه‌داری:
```bash
set OLLAMA_KEEP_ALIVE=2h      (ویندوز)
export OLLAMA_KEEP_ALIVE=2h   (لینوکس/مک)
```
مقدار `0` یعنی بلافاصله آزاد شود (برای رایانهٔ کم‌حافظه).

### پیش‌بارگذاری دستی
در پنل «عیب‌یابی»، ردیف **«در حافظه»** وضعیت را نشان می‌دهد و دکمهٔ
**«بارگذاری مدل»** مدل را از پیش در حافظه می‌نشاند — بعد از آن هر تحلیل
فقط زمان تولید متن را صرف می‌کند.

### زمان تقریبی هر تحلیل (i5-12400، CPU تنها)
| مدل | بارگذاری اول | هر تحلیل |
|---|---|---|
| `qwen3.5:4b` | ۱۵–۲۵ ثانیه | ۳۰–۴۰ ثانیه |
| `qwen3.5:9b` | ۳۰–۶۰ ثانیه | ۷۰–۱۰۰ ثانیه |
| `gemma4:12b` | ۶۰–۹۰ ثانیه | ۱۰۰–۱۴۰ ثانیه |

نتیجه در پایگاه داده ذخیره می‌شود؛ دفعهٔ بعد همان تحلیل از کش می‌آید و
دوباره محاسبه نمی‌شود.

## خطای «پاسخ مدل JSON معتبر نبود»

این خطا یعنی مدل وصل بود و جواب داد، ولی خروجی‌اش JSON معتبر نبود.
چهار علت، به‌ترتیب شیوع:

| علت | نشانه | رفع |
|---|---|---|
| **بریدگی پاسخ** | `done_reason: length` | سقف توکن بالا رفت (۳۵۰ → ۹۰۰) |
| متن اضافه پیش/پس JSON | «حتماً! این تحلیل است:» | استخراج اولین شیء JSON |
| بلوک کد ```` ```json ```` | پاسخ داخل سه بک‌تیک | حذف خودکار حصار |
| نقل‌قول فارسی « » | JSON خراب ظاهری | تبدیل به `"` |

### سه لایهٔ دفاعی در نسخهٔ ۱٫۶

**۱. ترمیم پاسخ ناقص**
اگر پاسخ وسط رشته یا آرایه بریده باشد، خودکار بسته می‌شود:
```
ورودی : {"headline": "سود خالص ۵۲۵,۸۲۱ میلیون ریال", "findings": [{"kpi": "FI
خروجی : {"headline": "سود خالص ۵۲۵,۸۲۱ میلیون ریال", "findings": []}
```

**۲. تلاش دوم با پیام اصلاحی**
اگر ترمیم هم نشد، مدل یک‌بار دیگر با پاسخ قبلی و این تذکر صدا زده می‌شود:
«پاسخ قبلی JSON معتبر نبود. فقط یک شیء JSON کامل بنویس. حداکثر ۲ مورد در هر فهرست.»

**۳. نمایش پاسخ خام**
اگر هر دو تلاش شکست بخورد، تحلیل قاعده‌محور نمایش داده می‌شود **و** زیر آن
بخشی به نام «پاسخ خام مدل را ببینید» باز می‌شود که عیناً آنچه مدل گفته را
نشان می‌دهد — تا بدانید مشکل از کجاست.

### تنظیم دستی سقف توکن
```bash
set AI_MAX_TOKENS=1400      (ویندوز)
export AI_MAX_TOKENS=1400   (لینوکس/مک)
```
مقدار بیشتر = احتمال بریدگی کمتر، ولی تولید طولانی‌تر و کندتر.

## کدام مدل لازم است؟

فقط **یکی** الزامی است:

| نقش | مدل | الزامی؟ |
|---|---|---|
| تحلیل پنل | `qwen3.5:9b` | **بله** — تمام تحلیل‌ها با این انجام می‌شود |
| گفت‌وگو | `qwen3.5:4b` | نه — فقط برای حالت «سریع» در منوی انتخاب مدل |
| عمیق | `gemma4:12b` | نه — فقط برای تحلیل عمیق اختیاری |

اگر در پنل عیب‌یابی خط `–` کنار یک مدل دیدید، یعنی **اختیاری** است و نبودنش
مانع کار نیست. علامت `✗` فقط برای مدل تحلیل ظاهر می‌شود و آن هم واقعاً مشکل است.

در منوی انتخاب مدل، مدل‌های نصب‌نشده **غیرفعال** نشان داده می‌شوند تا انتخابشان
به خطا نخورد.

## صفحهٔ «گفت‌وگو با مدل»

در منوی کناری، بخش **سیستم** → **گفت‌وگو با مدل**.

این صفحه برای این ساخته شده که **بدون واسطه ببینید مدل متصل است یا نه**:

| عنصر | کار |
|---|---|
| نشانگر وضعیت | «متصل — آدرس · تأخیر» یا «قطع — علت» |
| دکمهٔ **آزمون اتصال** | یک پیام کوتاه به مدل می‌فرستد و زمان پاسخ را می‌گوید |
| کادر گفت‌وگو | پرسش آزاد؛ پاسخ **کلمه‌به‌کلمه** نوشته می‌شود |
| نوار پایین | مدل، مدت کل، زمان اولین کلمه، توکن بر ثانیه |

پاسخ تدریجی می‌آید. اگر چیزی در حال آمدن باشد، یعنی اتصال واقعاً برقرار است —
نه اینکه فقط یک پیام موفقیت نمایش داده شود.

تفاوت با پنل تحلیل: اینجا مدل **متن آزاد** می‌نویسد و اجباری به JSON ندارد.
مناسب پرسش‌های عمومی و آزمودن مدل.

## تحلیل کوتاه (بخشی)

در پایین هر صفحهٔ داشبورد دو دکمه هست:

| دکمه | چه می‌کند | زمان تقریبی |
|---|---|---|
| **تحلیل کوتاه** (پیش‌فرض) | فقط همین بخش را می‌خواند: یک تیتر، حداکثر یک یافته در هر دسته | ۲۵–۴۵ ثانیه |
| **کامل** | همهٔ شاخص‌های صفحه را می‌بیند | ۷۰–۹۵ ثانیه |

مثلاً در صفحهٔ **ناوگان**، «تحلیل کوتاه» فقط شاخص‌های ناوگان را می‌بیند:
تعداد دستگاه، بهره‌وری، انحراف تناژ، هزینهٔ هر تن — نه مالی و نه پرسنلی.

سقف خروجی تحلیل کوتاه ۴۲۰ توکن است (در مقابل ۹۰۰ در حالت کامل).

## بررسی اتصال از خط فرمان
```bash
curl -X POST http://127.0.0.1:8000/api/ai/chat -H "Content-Type: application/json" \
  -d "{\"messages\":[{\"role\":\"user\",\"content\":\"سلام\"}]}"
```
اگر `"status": "ok"` برگشت، مدل جواب می‌دهد. اگر `"status": "error"` بود،
متن `error` دقیقاً می‌گوید چه شده.

## اگر «گفت‌وگو با مدل» را در منو نمی‌بینید

سه جای مختلف برای دسترسی هست:

۱. **نوار بالا** — دکمهٔ «گفت‌وگو با مدل» کنار انتخاب سال (همیشه دیده می‌شود)
۲. **نوار کناری، کادر هوش مصنوعی** — دکمهٔ طلایی «گفت‌وگو با مدل»
۳. **منو** — بخش «سیستم»، آخرین آیتم

### علتی که این اتفاق می‌افتاد
منو ده آیتم دارد و در ارتفاع‌های کم (۷۶۸ پیکسل) آیتم دهم زیر ناحیهٔ دید می‌رفت.
نوار اسکرول هم نامرئی بود و کاربر متوجه نمی‌شد چیزی پایین‌تر هست. از نسخهٔ ۱٫۹:

- فاصله‌های منو فشرده شدند
- نوار اسکرول قابل دیدن شد
- دکمه در نوار بالا هم اضافه شد

### اگر باز هم دیده نشد
دو نشانهٔ قطعی که نسخهٔ درست اجرا شده:

```bash
python -c "import app.config as c; print(c.APP_VERSION)"
```
باید `1.9.0` بدهد. اگر عدد کمتر داد، پوشهٔ قدیمی اجرا شده است.

و در مرورگر، منبع صفحه (Ctrl+U) را باز کنید و دنبال این خط بگردید:
```html
<script src="/static/app.js?v=1.9.0"></script>
```
اگر `?v=` ندارد یا نسخهٔ قدیمی است، سرور قدیمی در حال اجراست.
اگر **دارد** ولی دکمه‌ها نیستند، مرورگر فایل قدیمی را نگه داشته —
`Ctrl+Shift+R` بزنید.

## جلوگیری از حافظهٔ مرورگر
از نسخهٔ ۱٫۹، همهٔ فایل‌های JS و CSS با `?v=<نسخه>` بارگذاری می‌شوند و
پاسخ سرور `Cache-Control: no-cache` دارد. یعنی با هر نسخهٔ تازه، مرورگر
نسخهٔ جدید را می‌گیرد — بدون نیاز به پاک کردن حافظه.
